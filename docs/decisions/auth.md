# auth 결정 기록

인증, 토큰, 보안 wiring의 근거와 이력을 둔다. 현재 규칙은 `architecture` 스킬이 단일 소스다.

## 클라이언트 분리와 소셜 토큰 로그인

**클라이언트 분리 (2026-11-15 결정, 이슈 #181)**: 클라이언트를 원스토어에 배포하는 React Native 앱(Android만 대상)과 비회원 전용 웹으로 나눴다. 로그인, 페어링 추천, 모임 열기, 모임장 관리 같은 회원 기능은 앱이 맡는다. 참여, 정산 기록, 분담금 확인, 익명 피드백은 웹이 기존 참여 토큰과 개인 링크 토큰으로 처리한다. 앱은 카카오와 구글 네이티브 SDK로 로그인하므로 서버는 인가 코드 대신 소셜 토큰을 받아 검증한다. 네이버 로그인은 범위에 넣지 않았다.

**소셜 토큰 검증 (2026-11-15 결정, 이슈 #181)**: 구글은 ID 토큰의 서명, 발급자, `aud`, 만료를 검증한다. 발급자는 `https://accounts.google.com`과 `accounts.google.com`을 모두 허용한다. 구글이 두 형태로 발급할 수 있기 때문이다. `aud`는 앱이 `serverClientId`로 지정하는 웹 클라이언트 ID다. 카카오는 `/v1/user/access_token_info`가 돌려주는 `app_id`가 우리 앱 ID와 같은지 확인한 뒤 사용자 정보를 조회한다. 사용자 정보 조회만으로는 다른 앱이 발급한 액세스 토큰도 통과하므로, 다른 서비스에 로그인한 사용자의 토큰으로 이 서비스에 로그인할 수 있기 때문이다. 이 검증은 `SocialClient` 구현체의 책임이고 Service는 제공자별 사정을 모른다.

**소셜 토큰 에러 매핑 (2026-11-15 결정, 이슈 #181)**: 만료되었거나 형식이 잘못된 토큰은 클라이언트 잘못이라 400 `INVALID_SOCIAL_TOKEN`이다. 카카오의 401과 400 응답, 구글의 `BadJwtException`이 여기에 해당한다. 카카오가 일시적인 내부 오류에 쓰는 400(`-1`)도 이 코드로 응답하게 되는 한계가 있고, 드물어서 코드를 나누지 않았다. 공개키(JWKS)를 가져오지 못하거나 카카오 서버가 실패한 경우는 토큰의 잘못이 아니므로 500 `OAUTH_TOKEN_VERIFICATION_FAILED`다(#223에서 503 `OAUTH_TOKEN_VERIFICATION_UNAVAILABLE`로 변경). 이전에는 구글 검증 실패가 모두 500이어서 만료된 토큰이 서버 오류로 보였다. `INVALID_AUTHORIZATION_CODE`와 `OAUTH_TOKEN_EXCHANGE_FAILED`는 이 두 코드로 대체했고, 에러 코드 이름이 바뀌므로 클라이언트 계약이 바뀐다.

**VerifySocialTokenUseCase (2026-11-15 결정, 이슈 #181)**: `ExchangeSocialCodeUseCase`는 삭제하지 않고 `VerifySocialTokenUseCase`로 이름을 바꿨다. 삭제하면 제공자를 고르는 로직이 로그인과 가입 Service에 중복된다. 이름의 "교환"은 구현 방식이라 의도인 "소셜 신원 확인"으로 바꿨다.

**리프레시 토큰 전달 (2026-11-15 결정, 이슈 #181)**: 리프레시 토큰을 쿠키가 아니라 응답 바디로 전달하고, 재발급과 로그아웃은 요청 바디로 받는다. 앱은 Android Keystore 기반 보안 저장소에 보관한다. 웹에는 로그인이 없어서 `RefreshTokenCookieFactory`와 `refresh-token.cookie-secure`를 지웠다. RTR 회전과 `consume` 규칙은 그대로다. 재발급의 빈 토큰은 요청 DTO의 `@NotBlank`가 400으로 막고, 저장되지 않은 토큰은 도메인이 401(`REFRESH_TOKEN_NOT_FOUND`)로 응답한다. 형식 검증은 경계가 맡고 존재 여부는 도메인이 판단하므로 `RefreshService`의 null 분기도 지웠다. 로그아웃은 본문이 없어도 204다. 리프레시 토큰의 기본 만료 시간은 7일에서 30일로 늘렸다. 앱 사용자는 한 달에 한 번 열어도 로그인이 유지되기를 기대하고, 재발급할 때마다 만료가 새로 시작하므로 쓰는 동안은 계속 유지된다. 설정은 `REFRESH_TOKEN_EXPIRATION_TIME`으로 바꾼다.

**CORS와 CSRF (2026-11-15 결정, 이슈 #181)**: 쿠키를 쓰지 않으므로 `allowCredentials`를 껐다. 앱은 네이티브 HTTP라 CORS 대상이 아니어서 허용 오리진은 비회원 웹만 남는다. 브라우저가 인증 정보를 자동으로 붙이는 수단이 없으므로 `SameSite=Strict`에 기대던 CSRF 방어도 필요 없다.

**앱이 지킬 것 (2026-11-15 결정, 이슈 #181)**: 재발급 요청은 한 번에 하나만 보내야 한다. 같은 토큰으로 동시에 요청하면 두 번째가 401이 된다. 새 리프레시 토큰은 보안 저장소에 쓴 뒤에 사용한다. 재발급 응답이 앱에 닿지 못하면 이전 토큰은 이미 소비돼 재로그인이 필요하다. 이 재로그인이 실제로 자주 관측되면 소비한 토큰을 잠시 유지하는 유예 시간을 별도 이슈로 다룬다. 구글 로그인은 `serverClientId`에 웹 클라이언트 ID를 지정해야 한다. 카카오 로그인은 이메일과 프로필 동의 항목을 요청해야 하고, 빠지면 400 `SOCIAL_REQUIRED_INFO_MISSING`이다. 미가입 회원은 `login`이 404이므로 약관 동의를 거친 뒤 같은 토큰으로 `signup`을 부른다.

**택하지 않은 안 (2026-11-15 결정, 이슈 #181)**: 구글 `nonce`로 ID 토큰 재사용을 막는 안은 택하지 않았다. 서버가 nonce를 발급하는 엔드포인트와 저장소가 새로 필요하다. ID 토큰은 약 1시간 유효하고 HTTPS로만 전달되므로 지금은 수용한다. 재사용을 통한 탈취가 관측되면 재검토한다.

**구글 공개키 요청 타임아웃 (2026-11-22 결정, 이슈 #223)**: `NimbusJwtDecoder.withJwkSetUri`의 기본 `RestOperations`는 연결과 읽기 타임아웃이 모두 30초다. `spring-security-oauth2-jose` 7.0.9 소스에서 확인했고, JDK 프로퍼티 `sun.net.client.defaultConnectTimeout`과 `defaultReadTimeout`이 있으면 그 값을 따른다. 공개키는 캐시되므로 평소에는 영향이 없지만, 공개키를 갱신하거나 구글에 장애가 있으면 로그인과 비회원 참여 요청이 최대 약 60초 기다린다. 그래서 `OAuthConfig`가 연결 3초, 읽기 3초인 `RestTemplate`을 디코더에 지정한다. 공개키 요청은 평소 수백 ms 안에 끝나므로 지연은 사실상 장애다. 오래 기다리게 하는 것보다 빨리 실패시켜 다시 시도하게 하는 편이 사용자에게 낫다. 최악 대기를 6초로 맞춰 앱의 요청 타임아웃보다 서버가 먼저 응답하게 했다. 공유 `RestClient`의 읽기 5초를 따르는 안은 최악이 8초라 택하지 않았다. 값은 프로파일별로 다르게 할 이유가 없고 `RestClientConfig`도 상수라서 `GoogleOAuthProperties`나 yaml로 빼지 않았다. 타임아웃 동작을 로컬 HTTP 서버로 응답을 지연시켜 검증하는 테스트는 저장소에 선례가 없는 종류라 넣지 않았다. 공개키 요청 실패가 `JwtException`으로 올라와 503으로 바뀌는 것은 `GoogleSocialClientTest`가 검증한다.

**소셜 검증 실패의 503 전환 (2026-11-22 결정, 이슈 #223)**: 공개키 요청 실패, 카카오 `access_token_info` 실패, 카카오 사용자 정보 조회 실패는 모두 사용자가 잠시 후 다시 시도하면 되는 외부 서비스 장애다. 500은 서버 버그처럼 읽혀 클라이언트가 재시도 안내를 보여 주기 어렵다. 그래서 500 `OAUTH_TOKEN_VERIFICATION_FAILED`와 `OAUTH_MEMBER_INFO_FETCH_FAILED`를 503 `OAUTH_TOKEN_VERIFICATION_UNAVAILABLE`과 `OAUTH_MEMBER_INFO_UNAVAILABLE`로 바꿨다. 이름은 `error-handling` 스킬의 503 어휘(`*_UNAVAILABLE`)를 따랐고, 예외도 `ServiceUnavailableException`을 상속하는 `SocialTokenVerificationUnavailableException`과 `SocialMemberInfoUnavailableException`으로 바꿨다. 구글만 503으로 바꾸는 안과 토큰 검증 코드만 바꾸는 안은 택하지 않았다. 같은 로그인 요청에서 카카오의 같은 종류 실패가 500과 503으로 갈려 클라이언트가 처리를 나눠야 하기 때문이다. 알려진 한계가 하나 있다. 카카오의 호출 한도 초과나 앱 권한 문제처럼 토큰 잘못이 아닌 4xx도 503이 되고, 이 경우 재시도로는 풀리지 않을 수 있다. 드물어서 코드를 나누지 않았다. 에러 코드 이름과 상태가 바뀌므로 클라이언트 계약이 바뀐다. 앱과 웹이 아직 배포되지 않아 지금 바꾼다.

## 보안 필터의 auth domain 참조

**(2026-10-29 결정, 이슈 #147)**: `global.security`의 인증 필터와 인증 실패 핸들러는 `auth`의 `domain` 타입을 참조할 수 있다. 필터는 인터페이스(`AccessTokenProvider`, `BlacklistAccessTokenRepository`, `WithdrawnMemberRepository`(#201에서 추가))를, 핸들러는 에러 코드(`AuthErrorCode`)를 참조한다. 요청의 토큰을 검증해 인증 정보를 채우고 인증 실패를 응답하는 것은 보안 wiring 목적이기 때문이다. 구현체(`JwtAccessTokenProvider` 등)와 `infrastructure` 패키지는 참조하지 않는다. 토큰 Provider도 Repository처럼 `domain`에 인터페이스를 두고 `infrastructure`가 구현한다. gathering의 `GatheringTokenProvider`와 같은 구조다. 인터페이스가 기본 이름을 갖고, 구현체 이름에는 방식을 붙인다(`JwtAccessTokenProvider`, `UuidRefreshTokenProvider`).

## Redis 장애 때의 인증 필터

**(2026-11-24 결정, 이슈 #229)**: `JwtAuthenticationFilter`가 블랙리스트와 탈퇴한 회원 id를 Redis로 조회하다 `DataAccessException`을 만나면, 경고 로그를 남기고 인증하지 않은 채 요청을 넘긴다. 만료된 토큰을 비회원으로 보는 기존 동작과 같다. 이전에는 예외가 필터 밖으로 나가 500이 됐고, 로그인한 사용자는 모든 요청에 Bearer 토큰을 붙이므로 Redis를 쓰지 않는 공개 엔드포인트(페어링 추천, 맛집 조회)도 실패했다. 카탈로그 캐시(`RedisCatalogCache`)가 장애 때 DB로 내려가도록 만든 방어를 이 필터가 무력화하고 있었다. 필터는 요청 속성에 `TokenStoreUnavailableException`을 남기고, 인증이 필요한 엔드포인트에서는 `CustomAuthenticationEntryPoint`가 이 속성을 보고 401 대신 503 `TOKEN_STORE_UNAVAILABLE`로 응답한다. 클라이언트가 재로그인으로 오해하지 않게 하기 위해서다. 로그에는 토큰 원문이 남지 않도록 예외 메시지 대신 클래스 이름만 남긴다. 필터의 정상 경로는 바꾸지 않았다.

**택하지 않은 안 (2026-11-24 결정, 이슈 #229)**: 필터에서 Redis 장애 때 모든 요청을 거절하는 안은 택하지 않았다. 안전하지만 Redis를 쓰지 않는 공개 엔드포인트까지 막아 장애 범위가 넓어진다.

**알려진 한계 (2026-11-24 결정, 이슈 #229)**: Redis 장애 중에는 폐기된 토큰과 탈퇴한 회원의 토큰이 공개 엔드포인트에서 비회원으로만 처리된다. 보호된 자원에는 통과하지 않으므로 권한 상승은 없다. 대신 장애 중에는 로그인한 회원의 싫어요 조합 제외(페어링 추천)가 적용되지 않아 싫어요로 표시한 조합이 다시 추천될 수 있고, 감사 로그의 행위자도 익명으로 남는다. 둘 다 장애 동안만 생기는 수용 가능한 저하라서 코드로 막지 않았다. 다만 로그아웃은 공개 엔드포인트라, 장애 중에는 필터가 인증하지 않아 액세스 토큰을 블랙리스트에 올리지 않는다. 이 한계는 로그아웃이 리프레시 토큰을 지우는 Redis 호출도 같은 장애로 실패하는 것과 함께 받아들였다.

## 로그아웃

**로그아웃 (2026-11-01 결정, 이슈 #156)**: 로그아웃은 이 기기의 세션만 끊고, 토큰이 없거나 만료돼도 204를 반환한다. 그래서 `LOGOUT`은 인증 없이 호출할 수 있고, 쿠키의 리프레시 토큰 하나를 `consume`으로 지운다. 액세스 토큰은 필터가 인증한 유효한 토큰일 때만 블랙리스트에 올린다. 이전에는 로그아웃에 인증이 필요해서, 액세스 토큰이 만료되면 401이 나고 리프레시 토큰이 남았다. 쿠키 `Path`도 재발급 엔드포인트라 로그아웃 요청에 쿠키가 실리지 않았다. 사용자가 로그아웃을 눌렀을 때 오류를 보여 주지 않고, 누른 기기만 끊는 것이 일반적인 기대이기 때문이다. 만료된 액세스 토큰을 로그아웃에서만 허용하는 안은 택하지 않았다. `AccessTokenProvider`에 만료를 무시하는 파싱이 생기고, 오래전에 유출된 토큰으로도 세션을 끊을 수 있기 때문이다. 회원 탈퇴는 모든 기기를 끊어야 하므로 `MemberDeletedEventListener`가 `ForceRevokeUseCase`로 회원의 리프레시 토큰을 모두 지우고 `LogoutUseCase`로 액세스 토큰을 블랙리스트에 올린다. 이미 발급된 옛 `Path` 쿠키는 처리하지 않았다. 결정 시점에 운영 배포가 없었기 때문이다.

**(2026-11-15 결정, 이슈 #181)**: 위 문단의 쿠키 전제는 리프레시 토큰을 요청 바디로 받으면서 없어졌다. 로그아웃은 이제 바디의 리프레시 토큰 하나를 `consume`으로 지우고, 본문이 없거나 토큰이 없어도 204를 반환하는 규칙은 그대로다. 쿠키 `Path` 문제는 쿠키를 제거하면서 함께 사라졌다.

## 탈퇴한 회원의 액세스 토큰

**(2026-11-18 결정, 이슈 #201)**: 회원이 탈퇴하면 탈퇴한 회원 id를 액세스 토큰 유효시간(7200초)만큼 Redis에 남기고, 필터가 이 id의 액세스 토큰을 인증하지 않는다. 이전에는 탈퇴를 요청한 기기의 토큰만 블랙리스트에 올라 다른 기기의 토큰이 최대 2시간 유효했고, 필터가 회원 존재를 확인하지 않아 그 토큰으로 `POST /api/v1/gatherings`를 호출하면 존재하지 않는 회원이 모임장인 모임이 만들어졌다. 요청마다 DB로 회원 존재를 확인하는 안은 택하지 않았다. 기존 블랙리스트와 같은 Redis 방식이면 요청당 DB 조회가 늘지 않고 구조도 같기 때문이다. 필터가 요청마다 Redis를 한 번 더 조회한다.

**(2026-11-18 결정, 이슈 #201)**: 블랙리스트에 전달하는 남은 시간이 0초가 될 수 있다. `@TimeToLive`가 0이면 Redis 키가 만료되지 않고 남는 것을 테스트로 재현했다. 그래서 `BlacklistAccessTokenRepositoryImpl.save`가 최소 1초를 적용한다.

**(2026-11-18 결정, 이슈 #201)**: 탈퇴 리스너(`AFTER_COMMIT`)가 실패해도 API는 500이 아니라 204를 반환한다. 테스트로 확인한 실제 동작이다. 회원 삭제는 이미 커밋됐고 Spring이 `TransactionSynchronization.afterCompletion threw exception`을 ERROR로 남길 뿐이다. 응답 처리는 바꾸지 않고 테스트로 고정했다. 한계가 둘 있다. 탈퇴한 회원 id를 남기는 Redis 쓰기가 실패하면 다른 기기의 액세스 토큰이 최대 2시간 유효하다. 같은 리스너의 나머지 정리(요청 기기의 블랙리스트, 리프레시 토큰 삭제)도 함께 건너뛰지만, 재발급은 회원 존재를 확인하므로 노출은 액세스 토큰 2시간으로 한정된다. 또 알림 없이 Spring의 ERROR 로그만 남는다. 이 실패가 관측되면 알림이나 재시도를 도입한다.

**(2026-11-18 결정, 이슈 #201)**: 닉네임은 최대 20자(`MemberPolicy.MAX_NICKNAME_LENGTH`)다. `member.nickname` 컬럼은 255자라 `UpdateMemberRequest.nickname`에 길이 제한이 없으면 컬럼을 넘는 값에서 500이 날 수 있었다. 카카오 닉네임 한도와 기존 요청의 `@Size(max = 20)` 관례를 따랐다. 가입 시 소셜 닉네임이 넘으면 가입을 거절하지 않고 잘라서 저장한다. 소셜 쪽 길이는 우리가 정할 수 없어 거절하면 가입할 수 없는 회원이 생기기 때문이다. 길이는 `@Size`와 같은 UTF-16 단위로 세고, 자르는 위치가 이모지 한가운데이면 이모지를 통째로 버린다.

## 401 응답 헤더

**401 응답 헤더 (2026-11-01 결정, 이슈 #156)**: `CustomAuthenticationEntryPoint`는 401 응답에 `WWW-Authenticate: Bearer realm="symphonia"` 헤더를 넣는다. RFC 9110과 RFC 6750이 401 응답에 인증 방식을 알리도록 요구하기 때문이다. RFC 6750은 `Bearer` 뒤에 인증 매개변수를 하나 이상 요구해서 `realm`을 붙인다. `GlobalExceptionHandler`가 응답하는 401(`REFRESH_TOKEN_NOT_FOUND`)에는 넣지 않는다. 재발급은 Bearer가 아니라 쿠키로 인증하고, 헤더를 넣으면 `common`이 인증 방식을 알아야 하기 때문이다.

**(2026-11-15 결정, 이슈 #181)**: 재발급은 이제 쿠키가 아니라 요청 바디의 리프레시 토큰으로 인증한다. Bearer가 아니라는 점은 같으므로 `REFRESH_TOKEN_NOT_FOUND`에 헤더를 넣지 않는 규칙도 그대로다.

## Rate Limiting 미적용

**Rate Limiting 미적용 (2026-10-08 결정, 이슈 #83)**: 앱 단 IP별 rate limit(`RateLimitFilter`)을 제거했다. signup·login은 일회용 OAuth 인가 코드를, refresh는 추측할 수 없는 UUID 리프레시 토큰을 받으므로 무차별 대입이 성립하지 않는다. 대량 요청 방어는 요청이 앱에 닿기 전에 막는 LB/WAF(예: Cloud Armor)가 맡는 편이 낫다. 필터를 유지하려면 프록시 뒤 IP 식별과 `INCR`/`EXPIRE` 원자화(Lua)를 함께 고쳐야 했는데, 그 비용에 비해 실익이 작아 택하지 않았다. 잘못된 인가 코드로 반복 호출해 카카오·구글 API 호출 한도를 소모시키는 공격이 관측되거나, 비밀번호 로그인처럼 대입 가능한 입력을 받는 엔드포인트가 생기면 재검토한다.

**(2026-11-15 결정, 이슈 #181)**: 위 문단의 "일회용 인가 코드" 전제는 소셜 토큰 로그인으로 달라졌다. signup과 login은 이제 임의의 소셜 토큰을 받고, 카카오는 요청마다 외부 API를 두 번 호출한다. 구글은 공개키를 캐시해 서버에서 검증하므로 호출 한도를 쓰지 않는다. 그래서 잘못된 토큰으로 카카오 호출 한도를 소모시키는 공격이 위에서 정한 재검토 조건에 더 가까워졌다. 아직 관측된 공격이 없고 외부 호출에 연결 3초와 읽기 3~5초 제한이 있어서 이번에도 앱 단 rate limit은 넣지 않고 LB/WAF가 맡는다. 카카오 호출 한도 소모가 관측되면 재검토한다.

## 클라이언트 IP 식별

**클라이언트 IP 식별 (2026-10-08 결정, 이슈 #83)**: 클라이언트 IP는 감사 로그(`AuditLogRecorder`)의 `ip` 필드에만 쓰인다. `server.forward-headers-strategy: native`로 Tomcat `RemoteIpValve`를 켜고, `server.tomcat.remoteip.internal-proxies`(`TRUSTED_PROXIES` 환경변수, 기본값은 Spring Boot의 사설 IP 대역)에 든 프록시가 보낸 `X-Forwarded-For`만 반영한다. 그래서 IP는 어디서든 `HttpServletRequest.getRemoteAddr()`로 구하고, 별도 IP 추출 유틸을 두지 않는다. `framework` 전략(`ForwardedHeaderFilter`)은 헤더를 무조건 신뢰해 위조에 열려 있어 택하지 않았다. 신뢰 프록시 목록이 실제 LB 대역과 어긋나면 헤더가 무시되어 LB IP가 남을 뿐 위조에 열리지는 않으므로(#178에서 변경), 동작 검증은 테스트가 아니라 배포 시 `TRUSTED_PROXIES`를 넣고 감사 로그를 확인하는 것으로 한다. MockMvc는 Tomcat을 거치지 않아 이 동작을 검증할 수 없고, 실제 포트를 띄우는 테스트는 우리 코드가 아니라 Tomcat 구현을 검증하게 되어 두지 않았다. IP를 인가·차단 판단에 쓰기 시작하면 테스트 추가를 재검토한다.

**(2026-11-08 결정, 이슈 #178)**: #83 문단의 "위조에 열리지는 않는다"는 신뢰 프록시 목록이 실제 LB 대역보다 좁을 때만 맞다. 목록이 넓으면 그 대역 안의 다른 호스트가 `X-Forwarded-For`를 위조해 감사 로그에 원하는 IP를 남길 수 있다. 기본값인 사설 IP 대역 전체가 여기에 해당한다. 그래서 운영 환경의 `TRUSTED_PROXIES`에는 실제 LB 대역만 넣고, 앱 포트에는 LB만 접근할 수 있게 네트워크를 막는다. LB는 접속한 IP를 `X-Forwarded-For` 끝에 덧붙여야 한다. `RemoteIpValve`는 헤더를 오른쪽부터 읽어 신뢰 프록시가 아닌 첫 IP를 클라이언트로 보므로, LB가 헤더를 그대로 넘기기만 하면 클라이언트가 보낸 값이 남는다. 반대로 LB가 접속 IP를 덧붙이면 그 왼쪽의 위조 값은 읽히지 않으므로 외부 헤더를 지우지 않아도 된다. 감사 로그의 IP는 인가와 차단 판단에 쓰지 않으므로, 위조돼도 기록이 틀릴 뿐 접근 통제가 뚫리지는 않는다. 그래서 테스트 없이 배포 시 감사 로그로 확인하는 #83의 검증 방식은 유지한다.
