# place 결정 기록

맛집 조회의 근거와 이력을 둔다. 현재 규칙은 `architecture` 스킬의 `place.md`가 단일 소스다. 안주의 맛집 검색어 컬럼은 `catalog.md`와 `persistence.md`에 있다.

## 외부 검색 선택

**(2026-11-15 결정, 이슈 #182)**: 맛집은 NAVER API HUB의 지역 검색으로 찾는다. 개발자센터(developers.naver.com)의 검색 API는 신규 발급이 2026년 7월 말에 중단되고 지원이 2027년 6월 30일에 끝나는 것으로 알려져 있다. 이 날짜는 블로그와 보도 같은 2차 자료 기준이고, 공식 공지 원문은 접속이 막혀 확인하지 못했다. API HUB 문서는 새 키가 NCP 콘솔의 Application에서 발급되고, 호출 주소(`naverapihub.apigw.ntruss.com`)와 인증 헤더(`X-NCP-APIGW-API-KEY-ID`, `X-NCP-APIGW-API-KEY`)가 개발자센터와 다르다고 설명한다. 하루 호출 한도는 25,000회이고 넘으면 429다. 이 키는 결제수단을 등록한 NCP 계정에서 발급했다. 사용자가 확인한 자료(NCP API HUB 가이드와 개발자센터 공지 32530)에 따르면 요금은 기본이 종량제이고 현재는 한시적 무료다. 일반 검색 API는 월 775,000건(하루 25,000건)의 공유 한도와 인증 키당 초당 50회 제한이 있고 넘으면 429다. 기존 개발자센터는 2026년 7월 31일 이전에 신청한 키만 2027년 6월 30일까지 유예된다. 이 내용은 직접 확인하지 못한 요약이라 공식 페이지와 다를 수 있다. 무료 기간이 끝나면 요금이 나올 수 있으므로 재검토 조건이다.

**표본 호출 결과**: `sort=comment`(리뷰 많은 순)로 `강남구 치킨`을 검색하면 이탈리아 음식, 햄버거, 스테이크가 나오고 치킨집이 없었다. `sort=random`(정확도순)은 호프와 치킨집이 나왔다. 그래서 정확도순을 쓴다. `mapx`와 `mapy`는 경도와 위도에 10의 7제곱을 곱한 정수 문자열이었다. 제목에는 `<b>` 태그와 `&amp;`가 섞여 와서 둘 다 풀어서 담는다. `display`의 기본값이 1이라 5를 명시한다.

## 호출 단위

**(2026-11-15 결정, 이슈 #182)**: 조회는 안주 하나를 받아 한 번 호출한다. 처음에는 추천 상위 조합의 안주 2~3개를 키워드별 그룹으로 한 번에 내려주는 안이었다. 이 안은 택하지 않았다. 모임 참여 화면과 정산 화면은 모임에 정해진 안주 하나만 다룬다. 추천 결과 화면에서도 사용자가 보지 않을 안주의 결과까지 미리 조회해 호출 한도와 응답 시간을 쓴다. 안주 하나 기준이면 병렬 호출, id 중복 제거, 그룹 응답이 필요 없다. 추천 결과 화면은 사용자가 조합을 눌렀을 때 조회한다.

안주 이름 문자열을 받는 안도 택하지 않았다. 아무 검색어로 하루 호출 한도를 쓸 수 있기 때문이다. 그래서 안주 id만 받고, 참여자 페어링 응답에 `anjuId`를 추가했다.

## 저장과 캐시

**(2026-11-15 결정, 이슈 #182)**: 검색 결과를 서버에 저장하거나 캐시하지 않고 요청마다 네이버를 호출한다. 처음에는 하루 호출 한도를 아끼려고 Redis에 10분만 담는 안이었다. 근거는 NAVER API HUB 서비스 이용약관(시행 2026년 10월 7일)이다. 검색 API 특약 1.3은 데이터(가공이나 파생물 포함)를 복사, 저장 또는 캐싱하는 행위를 금지하고 1.4에 해당하는 경우만 제외한다. 1.4는 서비스 연속성을 유지하는 데 필요한 범위에서 기기나 서버에 임시 보관을 허용하되 목적과 기간을 정한다. 기기 보관은 서비스 장애에 대응하거나 개인화 서비스를 제공하는 목적으로 24시간 또는 새 질의 시까지 중 더 짧은 기간이다. 서버 보관은 이력 조회 목적으로 최대 21일이고, 개인화 서비스 목적은 기기 보관과 같다. 호출 한도를 아끼려는 모든 사용자 공용의 서버 캐시는 이 목적들에 들지 않는다. 일반조건 7.3의 3번도 허용 범위를 넘는 복제와 저장(캐시 행위 포함)을 금지하고, 예시로 지역정보를 별도 데이터베이스로 관리하는 행위를 든다. 위반하면 9.4에 따라 클라이언트 아이디의 사용이 제한되거나 정지될 수 있다. 그러면 맛집 조회 전체를 쓸 수 없으므로 캐시의 이득이 위험보다 작다고 판단했다. 이 해석은 약관 문장을 읽은 판단이며 법률 자문이 아니다.

호출 한도에 주는 영향은 이렇다. 캐시가 없으면 호출 수가 맛집 조회 수와 같다. 하루 한도 25,000회를 1인당 하루 5회 조회로 어림하면 하루 활성 사용자 약 5,000명이다. 그 규모에 가까워지면 네이버에 한도 증설을 문의한다. 클라이언트가 기기에 마지막 결과를 장애 대응용으로 24시간 또는 새 질의 시까지 두는 것은 1.4가 허용하는 범위다. 호출을 줄이는 방법은 클라이언트가 화면에 표시 중인 결과를 같은 요청으로 다시 받지 않는 것으로 정했고, 기기 보관은 하지 않는다. 사용자별 키를 붙여 개인화 목적의 서버 캐시로 만드는 안은 택하지 않았다. 같은 지역과 안주에는 누구에게나 같은 결과라 개인화가 아니고, 새 질의가 오면 지워야 해서 절감이 거의 없고, 식별할 수 없는 비회원이 쓰기 때문이다. 서버에서 이력 조회 목적으로 최대 21일 보관하는 것은 "내가 본 맛집 이력" 같은 기능이 생길 때 다시 검토한다. 이때 보관은 목적별로 분리해야 한다. 개발자센터 공지에서는 같은 특약이 2.1부터 2.4로 번호가 매겨져 있고 내용은 같다(시행 2026년 9월 7일).

## 약관의 표시와 가공 조건

**(2026-11-15 결정, 이슈 #182)**: 검색 API 특약 1.2는 데이터를 독립적으로 가공 없이 노출하고, 순위와 내용을 수정, 변조 또는 왜곡하지 않으며, 원본의 출처를 표시하고 원본으로 이동할 링크를 제공하라고 한다. 특약 1.1은 BI 가이드에 따라 네이버 검색결과임을 표시하라고 한다. 특약 1.3과 일반조건 7.3의 4번은 검색결과가 표시되는 페이지에 광고를 노출하는 것을 금지한다. 서버는 정확도순(`sort=random`)으로 받은 순서를 그대로 내려주고, 응답의 `source`와 각 가게의 `link`로 출처와 원본 링크를 준다. 출처 표시와 광고 금지는 클라이언트가 지킨다. 특약 1.3은 데이터를 AI에 입력하거나 제3자에게 제공, 판매하는 행위와 검색 API를 활용해 수익을 얻는 행위도 금지한다. 코드가 이를 어기는 곳은 없지만, 서비스에 수익 모델이 생기면 이 조항을 먼저 확인해야 한다.

서버가 하는 가공은 이름의 HTML 태그와 엔티티 제거, 좌표의 도 단위 변환, 이름이 없거나 좌표를 읽을 수 없는 가게 제외다. 순위와 내용을 바꾸는 것이 아니라 화면에 표시할 수 있는 형식으로 정리하는 것이라고 판단했다. 이 판단이 약관의 "가공 없이"에 닿는지는 원문만으로 확정하기 어렵다. 문제가 되면 원본 값을 그대로 내려주고 클라이언트가 변환하는 방향으로 바꾼다.

## 지역명과 개인위치정보

**(2026-11-15 결정, 이슈 #182)**: 서버는 사용자 좌표를 받지 않고 클라이언트가 만든 지역명 문자열만 받는다. 서버가 개인위치정보를 전송받으면 저장하지 않아도 위치기반서비스사업 신고 대상이기 때문이다. 지역명은 한글, 숫자, 공백 30자로 제한한다. 외부 검색의 검색어에 그대로 들어가므로 임의의 문자열이 외부로 나가지 않게 하기 위해서다. 지역명은 GET 쿼리스트링으로 받는다. `GET /api/v1/pairings/recommendations`와 같은 방식이다. 앱은 지역명을 저장하거나 로그에 남기지 않지만 LB나 프록시의 접근 로그에는 남을 수 있다. 접근 로그에서 쿼리스트링을 빼는 일은 인프라에 요청해야 한다. POST 본문으로 받는 안은 이 위험을 줄이지만 조회에 POST를 쓰게 되어 택하지 않았다.

재검토 조건은 기기에서 변환한 지역명이 개인위치정보에 해당하는지 위치정보지원센터에 문의한 결과다. 해당하면 접근 로그의 처리를 다시 정한다. 지역명은 검색어로 네이버에 전송되므로, 일반조건 7.4의 7번(이용고객의 개인정보가 네이버나 네이버클라우드에 전송되지 않도록 하고, 불가피하면 고지와 동의를 받을 것)에 닿는지도 함께 확인한다.

## 호출 한도 방어

**(2026-11-15 결정, 이슈 #182)**: 조회는 비회원도 써야 해서 `permitAll`이고, 앱 단 rate limit은 두지 않는다(대량 요청 방어는 LB와 WAF의 몫이다). 그래서 앱이 할 수 있는 방어는 지역명 형식 검증과 안주 id 방식이다. 429는 하루 한도 초과와 키당 초당 50회 제한을 구분하지 않고 같은 코드로 응답한다. 캐시가 없어 모든 요청이 외부 검색을 호출하므로 순간적으로 몰리면 초당 제한에 먼저 걸릴 수 있다. 부하 테스트에서 확인하고, 이 경로의 LB나 WAF 요청 제한이 더 중요해졌다. 호출 한도가 소진되면 503과 `PLACE_SEARCH_LIMIT_EXCEEDED`로 응답하고, 클라이언트는 맛집 영역만 숨기면 페어링 화면은 그대로 쓸 수 있다. 이 경로에 대한 LB나 WAF의 요청 제한은 인프라 쪽 후속 작업이다.

## 트랜잭션 안의 외부 호출

**(2026-11-15 결정, 이슈 #182)**: `PlaceQueryService`는 다른 서비스처럼 `@QueryService`라서 읽기 전용 트랜잭션 안에서 외부 검색을 부른다. `LoginService`가 소셜 검증을 트랜잭션 안에서 부르는 것과 같은 방식이다. 외부 검색이 느리면 그동안 DB 커넥션을 쥔다. `global.config.RestClientConfig`의 공유 `RestClient`가 정한 타임아웃은 연결 3초, 읽기 5초이고, 이 빈은 소셜 로그인과 함께 쓴다. 캐시가 없어 모든 요청이 외부 검색을 부르므로 이 위험이 요청마다 적용된다. (#182에서 변경) `PlaceQueryService`를 `RecommendPlacesService`로 바꾸고 `@Service`로 두어 외부 검색이 트랜잭션 밖에서 실행된다. 근거는 `architecture.md`의 "외부 호출과 트랜잭션"에 있다.
