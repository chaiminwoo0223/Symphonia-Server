# place 결정 기록

맛집 조회의 근거와 이력을 둔다. 현재 규칙은 `architecture` 스킬의 `place.md`가 단일 소스다. 안주의 맛집 검색어 컬럼은 `catalog.md`와 `persistence.md`에 있다.

## 외부 검색 선택

**(2026-11-15 결정, 이슈 #182)**: 맛집은 NAVER API HUB의 지역 검색으로 찾는다. 개발자센터(developers.naver.com)의 검색 API는 신규 발급이 2026년 7월 말에 중단되고 지원이 2027년 6월 30일에 끝나는 것으로 알려져 있다. 이 날짜는 블로그와 보도 같은 2차 자료 기준이고, 공식 공지 원문은 접속이 막혀 확인하지 못했다. API HUB 문서는 새 키가 NCP 콘솔의 Application에서 발급되고, 호출 주소(`naverapihub.apigw.ntruss.com`)와 인증 헤더(`X-NCP-APIGW-API-KEY-ID`, `X-NCP-APIGW-API-KEY`)가 개발자센터와 다르다고 설명한다. 하루 호출 한도는 25,000회이고 넘으면 429다. 이 키는 결제수단을 등록한 NCP 계정에서 발급했다. 사용자가 확인한 자료(NCP API HUB 가이드와 개발자센터 공지 32530)에 따르면 요금은 기본이 종량제이고 현재는 한시적 무료다. 일반 검색 API는 월 775,000건(하루 25,000건)의 공유 한도와 인증 키당 초당 50회 제한이 있고 넘으면 429다. 기존 개발자센터는 2026년 7월 31일 이전에 신청한 키만 2027년 6월 30일까지 유예된다. 이 내용은 직접 확인하지 못한 요약이라 공식 페이지와 다를 수 있다. 무료 기간이 끝나면 요금이 나올 수 있으므로 재검토 조건이다.

**표본 호출 결과**: `sort=comment`(리뷰 많은 순)로 `강남구 치킨`을 검색하면 이탈리아 음식, 햄버거, 스테이크가 나오고 치킨집이 없었다. `sort=random`(정확도순)은 호프와 치킨집이 나왔다. 그래서 정확도순을 쓴다. `mapx`와 `mapy`는 경도와 위도에 10의 7제곱을 곱한 정수 문자열이었다. 제목에는 `<b>` 태그와 `&amp;`가 섞여 와서 둘 다 풀어서 담는다. `display`의 기본값이 1이라 5를 명시한다.

## 호출 단위

**(2026-11-15 결정, 이슈 #182)**: 조회는 안주 하나를 받아 한 번 호출한다. 처음에는 추천 상위 조합의 안주 2~3개를 키워드별 그룹으로 한 번에 내려주는 안이었다. 이 안은 택하지 않았다. 모임 참여 화면과 정산 화면은 모임에 정해진 안주 하나만 다룬다. 추천 결과 화면에서도 사용자가 보지 않을 안주의 결과까지 미리 조회해 호출 한도와 응답 시간을 쓴다. 안주 하나 기준이면 병렬 호출, id 중복 제거, 그룹 응답이 필요 없다. 추천 결과 화면은 사용자가 조합을 눌렀을 때 조회한다.

안주 이름 문자열을 받는 안도 택하지 않았다. 아무 검색어로 하루 호출 한도를 쓸 수 있기 때문이다. 그래서 안주 id만 받고, 참여자 페어링 응답에 `anjuId`를 추가했다.

## 저장과 캐시

**(2026-11-15 결정, 이슈 #182)**: 가게 정보는 DB에 저장하지 않고 Redis에 10분만 담는다. 이용약관이 검색 결과를 별도 DB에 복사하는 것을 금지하기 때문이다. 캐시는 하루 호출 한도를 아끼려는 용도라 몇 분 단위로 짧게 둔다. TTL은 `RedisCatalogCache`처럼 상수로 두고, 호출 한도 사용량을 보고 조정한다. 키는 검색어의 SHA-256이라 지역명이 Redis에 읽을 수 있는 글자로 남지 않는다. 결과가 없던 검색도 담아 같은 헛호출을 반복하지 않는다. Redis 장애는 `CatalogCache`와 같이 삼키고 외부 검색을 부른다. 안주 이름 대신 지정한 검색어를 쓰면 `와인바`, `호프`처럼 여러 안주가 같은 검색어를 공유해 적중률이 오른다. 다만 참여자마다 기기에서 만든 지역명이 달라지면 적중률이 낮아질 수 있어, 클라이언트가 구나 동 단위로 통일해 보내야 한다.

## 지역명과 개인위치정보

**(2026-11-15 결정, 이슈 #182)**: 서버는 사용자 좌표를 받지 않고 클라이언트가 만든 지역명 문자열만 받는다. 서버가 개인위치정보를 전송받으면 저장하지 않아도 위치기반서비스사업 신고 대상이기 때문이다. 지역명은 한글, 숫자, 공백 30자로 제한한다. 외부 검색의 검색어에 그대로 들어가므로 임의의 문자열이 새지 않게 하고, 캐시를 우회하려고 지역명을 늘리는 요청도 줄이기 위해서다. 지역명은 GET 쿼리스트링으로 받는다. `GET /api/v1/pairings/recommendations`와 같은 방식이다. 앱은 지역명을 저장하거나 로그에 남기지 않지만 LB나 프록시의 접근 로그에는 남을 수 있다. 접근 로그에서 쿼리스트링을 빼는 일은 인프라에 요청해야 한다. POST 본문으로 받는 안은 이 위험을 줄이지만 조회에 POST를 쓰게 되어 택하지 않았다.

재검토 조건은 기기에서 변환한 지역명이 개인위치정보에 해당하는지 위치정보지원센터에 문의한 결과다. 해당하면 캐시 키와 로그뿐 아니라 접근 로그의 처리도 다시 정한다.

## 호출 한도 방어

**(2026-11-15 결정, 이슈 #182)**: 조회는 비회원도 써야 해서 `permitAll`이고, 앱 단 rate limit은 두지 않는다(대량 요청 방어는 LB와 WAF의 몫이다). 그래서 앱이 할 수 있는 방어는 지역명 형식 검증과 안주 id 방식이다. 429는 하루 한도 초과와 키당 초당 50회 제한을 구분하지 않고 같은 코드로 응답한다. 캐시에 없는 요청이 순간적으로 몰리면 초당 제한에 먼저 걸릴 수 있어 부하 테스트에서 확인한다. 호출 한도가 소진되면 503과 `PLACE_SEARCH_LIMIT_EXCEEDED`로 응답하고, 클라이언트는 맛집 영역만 숨기면 페어링 화면은 그대로 쓸 수 있다. 이 경로에 대한 LB나 WAF의 요청 제한은 인프라 쪽 후속 작업이다.

## 트랜잭션 안의 외부 호출

**(2026-11-15 결정, 이슈 #182)**: `PlaceQueryService`는 다른 서비스처럼 `@QueryService`라서 읽기 전용 트랜잭션 안에서 외부 검색을 부른다. `LoginService`가 소셜 검증을 트랜잭션 안에서 부르는 것과 같은 방식이다. 외부 검색이 느리면 그동안 DB 커넥션을 쥔다. `global.config.RestClientConfig`의 공유 `RestClient`가 정한 타임아웃은 연결 3초, 읽기 5초이고, 이 빈은 소셜 로그인과 함께 쓴다. 캐시에 있으면 외부 호출 없이 끝난다. 부하 상황에서 커넥션 풀(기본 10개)이 부족해지면 호출 전에 트랜잭션을 끝내는 구조로 바꾸는 것을 재검토한다. 네이버 응답이 느린 상황은 외부 호출을 지연시킨 스텁으로 K6 스트레스 테스트를 하는 방법으로 확인할 수 있다.
