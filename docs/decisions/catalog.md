# catalog 결정 기록

카탈로그 도메인 분리와 다른 도메인에 여는 UseCase의 근거와 이력을 둔다. 현재 규칙은 `architecture` 스킬이 단일 소스다. 적재 규칙표와 데이터 선정은 `persistence.md`에 있다.

## pairing에서 catalog 분리

**(2026-10-27 결정, 이슈 #139)**: `pairing`에서 카탈로그를 `catalog` 도메인으로 분리한다. `catalog`는 음료, 안주, 음악 무드가 무엇이고 맛과 분위기 값이 얼마인지를 책임진다(#184에서 변경). `Drink`, `DrinkStyle`, `Anju`, `MusicMood`, 적재 규칙표, `*Reader`, 적재 러너가 여기에 속한다. `pairing`은 자리에 맞는 조합을 고르는 일을 책임진다. `Occasion`, 점수 계산, `Pairing`, `PairingFeedback`이 여기에 속한다. 근거는 두 가지다. 첫째, 적재 코드는 출처 데이터가 바뀔 때 바뀌고, 추천 코드는 점수 규칙이 바뀔 때 바뀐다. 분리 전 `pairing/domain` 파일 75개 중 34개가 적재용이었다. 둘째, 추천은 서비스의 핵심 도메인이고 카탈로그는 이를 받쳐 주는 지원 도메인이다. `pairing` 안에서 패키지만 나누는 안은 택하지 않았다. 크로스 도메인 규칙이 적용되지 않아 경계가 이름뿐이기 때문이다. 의존 방향은 `pairing → catalog` 한 방향이다. `FlavorProfile`과 `MoodProfile`(#184에서 변경)은 두 도메인이 각자 가진다. `catalog`의 것은 적재 규칙이 계산한 값을 담는다. `pairing`의 것은 유사도, 무게감, 분위기 적합도 같은 점수 계산 메서드를 가진다. 하나를 `common`에 두는 안은 택하지 않았다. `common`은 기술 공통 요소만 두는 곳이다. 또 점수 계산 메서드를 공유하면 `catalog`가 추천 규칙에 묶인다. `Drink.cutsRichnessOf`처럼 엔티티에 있던 점수 계산 메서드와 `Anju.conflictsWith` 같은 추천 필터는 `pairing`의 `PairingDrink`, `PairingAnju`, `PairingMusicMood`로 옮긴다(#140에서 변경). 음식 계열(`Harmonize`) 판정은 안주 속성으로 정해지는 분류라서 `catalog`에 둔다. `catalog`는 UseCase 세 개를 연다(#131에서 변경). `GetCatalogUseCase`는 `CatalogQuery`의 도수 상한 조건에 맞는 음료, 안주, 음악 무드를 `CatalogResult`로 일괄 조회한다. `VerifyCatalogReferencesUseCase`는 피드백이 id로 참조하는 음료, 안주, 음악 무드가 모두 있는지 한 번에 확인한다. `GetCatalogReferencesUseCase`는 id로 가리킨 음료, 안주, 음악 무드의 이름을 화면에 보여 줄 값으로 조회한다(#131에서 변경). 셋 다 부수효과 없는 단순 조회라서 Query 레벨 `CatalogQueryService` 하나가 함께 구현한다. 이름에 `Candidates`와 `Items`는 쓰지 않았다. `Items`는 무엇을 돌려주는지 알려 주지 않기 때문이다. `Candidate`도 같은 이유로 pairing 안의 이름에도 쓰지 않는다(#140에서 변경). `CatalogResult`에는 식별자, 표시 정보, 스타일 id, 맛과 분위기 축, 도수, 알레르기 유형, 음식 계열 판정 결과 등 추천에 필요한 값을 원시 값과 enum으로 담는다. `pairing`은 이를 `PairingDrink`, `PairingAnju`, `PairingMusicMood`로 바꾼다. 테이블과 FK는 바꾸지 않는다. 결정 문서의 위치는 design-decision 스킬의 #134 기준을 따른다(#134 결정은 `docs/decisions/harness.md`로 옮김, #178에서 변경). `catalog`에 적재 외의 실행 중 규칙이 생기면 그때 `catalog.md`를 만든다.

## 카탈로그 참조 검증과 변환 위치

**(2026-10-27 결정, 이슈 #140)**: `VerifyCatalogReferencesUseCase.verify`는 `CatalogReferencesQuery`(음료, 안주, 음악 무드 id, #131에서 `VerifyCatalogReferencesQuery`의 이름 변경)를 받고 반환값이 없다. 없는 대상이 있으면 catalog의 `DrinkNotFoundException`, `AnjuNotFoundException`, `MusicMoodNotFoundException`(#184에서 변경)을 던진다. 그래서 피드백 API의 404 응답과 에러 코드가 분리 전과 같다. `*Result`로 돌려주는 안은 택하지 않았다. pairing이 어느 대상이 없는지 다시 해석해 예외로 바꿔야 해서 분기만 늘어나기 때문이다. `CatalogResult`를 `PairingDrink`, `PairingAnju`, `PairingMusicMood`로 바꾸는 코드는 `PairingQueryService`의 private 메서드에 둔다. pairing의 domain은 catalog의 DTO를 참조할 수 없고, catalog의 DTO가 pairing 모델을 만들면 의존 방향이 거꾸로 된다. 호출하는 곳이 하나라서 `*Mapper`는 두지 않는다. 음식 계열 판정 결과는 `CatalogResult`에 계열마다 비트 하나를 둔 `harmonizeMask`로 담고, pairing은 두 값의 비트 AND만 본다. 쌍마다 판정 결과를 넘기는 안은 쌍이 약 18만 개라 택하지 않았다. 적재에서 빠진 안주를 지울 때는 catalog의 `AnjuRepository.findReferencedIds`가 `pairing_feedback`이 참조하는 안주를 걸러 낸다. 구현은 `pairing_feedback` 테이블을 네이티브 쿼리로 직접 조회한다. FK가 걸린 행을 지울 수 없다는 것은 `anju` 테이블의 영속성 제약이다. 또 #139에서 테이블과 FK를 그대로 두기로 해 테이블 결합은 이미 받아들였다. pairing이 UseCase를 열고 catalog가 이를 의존하는 안은 두 도메인이 서로를 의존하게 되어 택하지 않았다. catalog에 인터페이스를 두고 pairing이 구현하는 안은 pairing이 catalog의 enum이 아닌 타입을 참조하게 되어 택하지 않았다. 타입 이름에는 `Candidate`와 `Item`을 쓰지 않는다. 무엇인지 알려 주지 않기 때문이다. 같은 기준으로 `PairingCandidate`를 `PairingReasonContext`로, `CandidateThresholds`를 `SelectionThresholds`로 바꿨다.

## 안주 맛집 검색어

**(2026-11-15 결정, 이슈 #182)**: 안주를 맛집 검색어로 바꾸는 규칙은 `anju.place_keyword` 컬럼과 매핑표의 `place_keyword` 열에 둔다. 비워 둔 안주는 `Anju`를 만들 때 이름을 검색어로 쓰고, 컬럼은 `NOT NULL`로 저장한다. 안주 185개를 지역명과 함께 네이버 지역 검색으로 호출해 보니 약 4분의 3은 이름 그대로 관련 있는 가게가 나왔다. 나머지 약 4분의 1은 결과가 없거나(체다치즈큐브, 에다마메) 엉뚱했다(멜론은 성형외과와 노래방, 팝콘은 카페와 영화관). 그래서 이름이 맞지 않는 46개에만 검색어를 지정했고 검색어는 아홉 가지다. 이름만 검색어로 쓰는 안은 택하지 않았다. 가게가 없는 안주에서 엉뚱한 결과가 나오기 때문이다. 안주마다 검색어를 모두 지정하는 안은 택하지 않았다. 대부분은 이름으로 충분해서 매핑표만 길어지기 때문이다. 결과가 0건이면 숨기는 안은 택하지 않았다. 엉뚱한 결과는 5건이 그대로 나와서 건수로 걸러 낼 수 없다. 과일, 견과, 치즈 단품, 디저트처럼 가게 메뉴가 아닌 안주는 그 안주를 곁들이는 술집 유형(`와인바`, `호프`, `이자카야`, `전통주점`)으로 보낸다. 술자리 서비스에서 카페를 보여 주는 것보다 술집을 보여 주는 편이 흐름에 맞기 때문이다. 검색어는 `GetAnjuPlaceKeywordUseCase`가 안주 id 하나로 조회해 `AnjuPlaceKeywordResult`로 돌려주고, 기존 `CatalogQueryService`가 함께 구현한다. `AnjuRepository.findById`를 그대로 쓰므로 `GetCatalogReferencesUseCase`와 읽는 경로가 같다. 카탈로그 캐시에서 읽는 안은 전체 카탈로그를 매번 읽어야 해서 택하지 않았다.
